# OTPNET technical guide

*Looking for the simple guide? See [README.md](README.md). This page is the
command-line and protocol reference.*


Everything a new USB drive needs to join an OTPNET network: the client, a relay
node, a bootstrap (directory + ledger) service, offline dependency wheels, the
integration demo, and tests.

OTPNET sends email-style messages encrypted with a **one-time pad**: true-random
bytes that you and each contact share, generated by a hardware random number
generator and copied drive-to-drive **in person**. No computer, quantum or
otherwise, can break a correctly used one-time pad. The messages travel through
a 3-hop onion-routed relay network, and relay operators earn tokens for each
packet they forward.

> **V1 proof of concept.** The cryptography follows the spec, but the network
> services are simplified (see "Limitations"). Don't trust it with anything
> that matters yet.

---

## 1. Put the kit on a drive

1. Format the drive as **exFAT** (or ext4/APFS). FAT32 can't hold files over
   4 GB, and pads are usually bigger than that.
2. Unzip so the drive's root holds this `OTPNET/` folder.
3. Run setup once on each computer you'll use the drive from:

   | OS            | Command                            |
   |---------------|------------------------------------|
   | macOS / Linux | `sh OTPNET/setup.sh`               |
   | Windows       | double-click `OTPNET\setup.bat`    |

   Setup installs OTPNET's one dependency (`cryptography`) into
   `OTPNET/vendor/`, **offline** from `OTPNET/wheels/` (Linux x86_64/aarch64,
   macOS Intel/Apple Silicon, Windows x64; Python 3.9–3.14). Only on other
   platforms does it fall back to PyPI. The only thing the computer needs is
   **Python 3.9+**.

4. Check it: `python OTPNET/otpnet.py doctor`

Want to see the whole system work before setting anything up?
`python OTPNET/demo.py` runs Alice, Bob, a bootstrap and three relays on this
computer and checks every step (takes about 5 seconds).

In the commands below, `otpnet` means `python OTPNET/otpnet.py` (or use
`OTPNET/otpnet.sh` / `OTPNET\otpnet.bat`). By default all data goes in
`OTPNET/data/` on the drive; `--home DIR` picks another directory.

## 2. Create your identity

```sh
otpnet init --name alice \
            --listen 0.0.0.0:5001 --advertise 203.0.113.7:5001 \
            --bootstrap bootstrap.example.net:7000
```

* `--name`: your user id, which contacts see as the sender.
* `--listen`: where your inbox accepts deliveries. `--advertise` is the address
  other people's relays should connect to: your public IP, LAN IP, or a
  forwarded port. For a single-machine test, leave both at the default
  `127.0.0.1:5001`.
* `--bootstrap`: the network you're joining (whoever runs it gives you the
  address).
* `--mac`: `poly1305-otp` (default, information-theoretic) or `hmac-sha256`.

## 3. Exchange a pad with a contact (in person)

Meet, then plug **both** drives into one trusted computer (ideally offline) and
run from your drive:

```sh
otpnet pair --other /media/bob/OTPNET/data --size 64G
```

This generates the pad from the hardware TRNG (`/dev/hwrng` if it's fast
enough, or name a USB TRNG with `--entropy /dev/ttyACM0`). Hardware output is
XORed with `os.urandom()`. With no hardware RNG it says so and uses
`os.urandom()` alone, which is fine for testing. It writes the pad to your
drive, copies it to theirs and verifies the copy. It also records each other's
inbox address and routing key.

**Compare the printed fingerprint on both screens.** Each direction gets half
the pad: a 64 GB pad lets each of you send 32 GB. Every message costs its size
plus 32 bytes.

## 4. Use it

```sh
otpnet serve                                    # run your inbox (leave it running)
otpnet send --to bob --subject "Hi" --body "Meet at noon"
otpnet send --to bob --subject "Doc" --body-file note.txt --attach scan.pdf
otpnet inbox                                    # list received (--all includes sent)
otpnet read 3                                   # show message #3
otpnet contacts                                 # offsets and pad remaining per contact
otpnet                                          # no command: the friendly menu
otpnet contacts --set-address bob 198.51.100.4:5002   # contact moved
```

The recipient's inbox must be running when you send. Attachments are saved
under `OTPNET/data/inbox/<message id>/`.

## 5. Wallet

Every user and relay has a token wallet on the network ledger, named after its
user id (or relay id). New wallets receive the network's welcome tokens.
Sending a message costs the sum of the three relays' fees. Each fee is held in
escrow and goes to the relay only once it has passed the packet on; otherwise
it is refunded after 5 minutes.

```sh
otpnet wallet                                   # balance + recent activity
otpnet wallet history --limit 100
otpnet wallet send --to bob --amount 5 --memo "for the coffee"
otpnet wallet address                           # the name others pay you with
otpnet wallet backup /media/backup-stick/       # copy the wallet key somewhere safe
otpnet wallet --relay myrelay                   # a relay's wallet (earnings)
```

The wallet key is `ledger_secret` in `data/identity.json` (for a relay,
`data/relays/<id>/relay.json`). Anyone holding it can spend the tokens.
A relay's history shows what it earned but never who paid it.

## 6. Earn tokens: run a relay

```sh
otpnet relay --id myrelay --host 0.0.0.0 --port 8001 \
             --advertise-host 203.0.113.7 --fee 0.5 \
             --bootstrap bootstrap.example.net:7000
```

The relay registers with the directory and peels one onion layer per packet.
It is paid its fee only after the next hop confirms receipt. It never sees who
is talking to whom, and never sees message content.

## 7. Start a new network

```sh
otpnet bootstrap --host 0.0.0.0 --port 7000 --faucet 100
```

The bootstrap runs the relay directory and the token ledger. Each new account
gets `--faucet` tokens. Point everyone's `--bootstrap` at it, start at least
three relays, and you have a network.

## What's on the drive

```
OTPNET/
  Start OTPNET (...)   double-click launchers (menu)
  otpnet.py            launcher                 otpnet/      the code
  setup.sh setup.bat   one-time install         wheels/      offline dependencies
  otpnet.sh otpnet.bat wrappers                 vendor/      installed deps (per OS)
  demo.py              full-network self test   tests/       unit tests
  data/                created by `init`:
    config.json        your settings
    identity.json      routing key + ledger secret        <- keep private
    state.db           SQLite: tx/rx offsets, burn log, mailbox
    pads/<contact>.bin the one-time pads                  <- keep private
    inbox/             received attachments
```

## How a message is protected

1. The message is serialised (≤ 1 MB).
2. `tx_offset` is advanced **before** the pad is read, so those bytes are burned
   even if the send fails.
3. The first 32 bytes of the segment form a one-time MAC key; the rest is XORed
   with the message.
4. The packet carries `otp_offset` in plaintext. The MAC covers sender, offset,
   length and ciphertext, so a single flipped bit is detected.
5. Used pad bytes are overwritten with zeros on both drives
   (`--keep-used-pad` turns this off).
6. The receiver rejects `otp_offset < rx_offset` (replay). If
   `otp_offset > rx_offset`, it jumps forward and burns the gap (lost message),
   but **only after the MAC verifies**, so forged packets can't burn your pad.

## Limitations of this V1

* **Bootstrap is central.** The directory and ledger are a single service. A
  production design would use a DHT and a blockchain or federated mint.
* **The faucet is farmable.** Every new account, relays included, gets the
  welcome tokens, so tokens have no scarcity. A real network needs an issuance
  policy.
* **Payments are linkable.** The ledger sees which account funded which relays
  at the same moment. Blind-signed e-cash would fix this.
* **Traffic analysis.** Packet size isn't padded, and the circuit runs
  synchronously, so an observer of the whole network could correlate timing
  and size.
* **Exit relay knows the recipient.** The last relay learns the recipient's
  inbox address. There's no store-and-forward mailbox, so the recipient must be
  online.
* **Relay registration is unauthenticated, and transport is plain TCP.** The
  content is still onion- and OTP-encrypted, but the outer `hop` and
  `token_fee` fields are visible on the wire.
* **Wiping is best effort.** Flash wear-levelling can keep old copies of wiped
  pad blocks. Use full-disk encryption on the drive as well.
* **Physical security is everything.** Anyone who copies your drive can read
  future traffic with your contacts. Re-pair if a drive is lost.
